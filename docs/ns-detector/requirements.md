# 阶段性需求与质量门槛

本轮目标是在完整保留 Duck 全部检测能力的基础上，继续增强检测、界面和稳定性。本页区分开发范围与验收条件；列出工作项不表示代码已经编译、模拟器已经通过或真机已经验证。最终状态以对应提交的 Actions、测试报告和设备记录为准。

固定上游提交为 `b1135897cff4ddf01797f042bdd15f7d7e364e0d`。以下 18 项全部保留，新增功能不得通过移除慢探针、删减原生路径或取消进程隔离来达到性能目标：

## 应用签名与调试观察的解释边界

第 20 项计划从宿主 APK 的 `assets/ns_signing_policy.json` 读取版本化策略，形如：

```json
{
  "version": 1,
  "allowedPackage": "io.github.withite.nsdetector",
  "certificateSha256": ["<64 位十六进制的公开证书 SHA-256>"]
}
```

策略只包含公开证书指纹，不包含签名私钥或密码。策略必须绑定精确包名。没有策略、包名不匹配或首版未支持的多签名情形，应降低覆盖结论；明确策略与正式单签名证书不符可以形成 Warning。签名命中只说明采集到的当前证书与策略一致，不能认证系统或运行时。

证书轮换仅接受策略显式列出的当前证书；不能因旧证书出现在签名历史中就把未知新证书视为当前可信。Debug/testOnly 和用户主动调试是合法开发场景，不能单独宣称篡改或入侵。PackageManager、调试 API 或 `/proc/self/status` 不可用时，按原因区分 Support 和 Error。

本地签名策略、PackageManager、调试 API 与进程文件均可能受修改的系统或进程影响；这些观察不构成独立可信认证。正式安装包的长期签名与发布校验仍须由构建/离线签名流程完成。

## 每次合入的质量门槛

1. 上游保留守卫与全部架构守卫通过；新增模块补完版本适用性、主来源、误报条件和不可观察状态的 `EVIDENCE.md`。
2. 状态判定、签名 pin、损坏输入、权限不足、异常/取消、历史和筛选至少覆盖相关单元测试。更改公共契约时核对 API dump；新枚举逐一检查通知、导出、卡片和 SDK 消费方。
3. 完成所需 Gradle 单测、四 ABI Debug 构建、lint、依赖检查、SDK AAR 和独立消费示例；正式候选另验 Release 混淆与签名。不能把静态守卫通过写成 APK 构建通过。
4. 模拟器覆盖首次授权、拒绝非必要网络、扫描完成、筛选/清除、导出取消/旋转、进程重启；保存截图、窗口层级和日志。
5. 按[真机矩阵](test-matrix.md)验证硬件证明、SELinux、挂载、运行时、多进程与签名升级。缺少实机环境时明确记录，不发布准确率承诺。

## 性能验收方式

先记录各模块开始/完成时间、整轮耗时、失败与超时比例，再决定调度优化。目标仍为中端 arm64 真机离线快速扫描 p95 ≤ 5 秒，硬件证明、实验探针与联网步骤单列；当前没有可据此宣布达标的基准数据。

性能改善需要相同硬件、固件、权限、模块集合与冷热启动条件下的前后比较，并确认没有减少扫描覆盖。可取消协程不等于能够强制终止阻塞的系统调用；涉及原生阻塞的路径须公开其实际限制。
